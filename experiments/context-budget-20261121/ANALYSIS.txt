一、本轮到底改了哪里

本地 Python 工具修复了 NetworkX 图字段、Windows Bash 查找、多文件补丁
拼接缺少换行这三处问题。另为 bench/agent.py 增加请求前的历史预算检查：
优先缩短旧工具输出，再按完整调用组移除旧历史，保留原问题和最近两轮；
完整工具输出与请求审计落盘。预算使用保守字节估计，不是 Gemma tokenizer。
它可以验证请求大小受控，但可能丢失模型需要的旧证据，仍需真实任务验证。

上述 Python 改动没有放进官方 YAML 提交包，本次 Kaggle 实验没有执行它们。
官方测试的改动另做四组存档：
A 原配置；B 仅 include_thoughts=false；C 在 B 上输出上限 16384→8192；
D 在 C 上增加短读取、精简角色交接的提示词。D 的长度要求是软约束。
四组模型、角色、工具和单题 5 分钟/60 工具调用/100 轮保持一致。

二、实际测到了什么

在官方环境用 Gemma 4 31B QAT、4 张 L4 完成 3 题×4 组真实推理。
共 291 次模型请求，277 个带正数输入 usage 的正常响应。
A、B 各在 FastAPI 的 Architect 出现一次上下文超限；C、D 未观察到超限。
服务端拒绝原因是：输入至少 16385，加申请输出 16384，超过窗口 32768。
成功请求的最大输入不能当作被拒绝请求的精确输入长度。

更关键的结果是：四组都 0/3，12 次运行均达到 Agent 的 5 分钟超时。
12 份导出补丁均没有修改 rich/、fastapi/、requests/ 下的产品源码。
大多数调用停在 PM/Architect，只有 C/FastAPI 出现一次 Worker 请求。
因此当前证据支持“溢出有所缓解”，不支持“Agent 已能稳定修好问题”。
Rich 和 FastAPI 的目标断言仍失败。Requests 每组还有 185 个 httpbin fixture
递归依赖 setup errors，不能把这道题的验证失败全部算作模型能力问题。

三、为什么会这样

1. 输出额度也是窗口预算的一部分。原配置给单次输出留了半个窗口，
   很长的 Architect 调查历史就容易放不下。只隐藏思考历史没有解决这个问题。
   降到 8192 是本轮最小且有实际观测支持的缓解措施，但历史继续增长仍会撞线。

2. 不能把父 Runner 的压缩配置当作全系统保护。所测 google-adk 1.36.1
   的 AgentTool 创建独立子 Runner 时没有传入父 App；父 App 的压缩配置
   不会自动变成子 Runner 的配置。这解释了为什么 Architect 仍可能累积很长历史。
   这是源码机制解释，不代表所有调用都已经单独做过因果验证。

3. 更大的实际瓶颈是流程没有及时进入修改。现有任务契约、架构分析、
   报告和角色交接会消耗时间；本次轨迹中真正实施修复的机会太少。
   目前可以确认“实施阶段很少发生”，还不能只凭这 12 次就认定某一个提示词
   是唯一原因，也不能因此否定多 Agent 或本体建模本身。

4. 补丁是否非空不够。复现脚本、调试脚本和 .agent_state 都能让补丁非空，
   却没有修复目标。成功标准必须回到产品代码改动和原失败测试的变化。

四、建议下一轮按这个顺序做

先处理评测基础：在干净快照重现 Rich/FastAPI 的原失败；检查 Requests 的
fixture、依赖和官方执行命令。保留修复前/后的目标断言与回归结果。
环境问题单列，不靠修改评分测试掩盖。

第一轮只改一个变量：以 C 为基线，让 Architect 更早交还任务。
建议尝试“90 秒或 8 次调查工具调用，先到为准”；返回最多 3 个候选位置、
一个可执行复现命令、最小修复假设。剩余预算给 Worker 修改和验证。
这些数值是待测方案，不是已经实现的官方硬限制；先检查 harness 是否支持
子阶段预算。若只能写提示词，必须如实标注软约束并检查实际是否遵守。

同时固定提交清理：将状态文件放到仓库外或从最终补丁排除；检查导出补丁
在干净快照上的应用结果。不要直接删除所有新增脚本，区分有效回归测试
与临时调试文件，避免误删真正需要的交付内容。

第二轮再比较单 Agent 与精简多 Agent：同模型、同任务、同预算，先让每道
题至少重复 3 次，轮换运行顺序。记录修复率、首次产品代码修改时间、
角色调用数、上下文超限、目标测试结果和运行成本。

最后才加架构图/本体：拿已经能走完修复闭环的基线，加图与不加图做对照。
重点看候选文件是否更准、无关读取是否减少、首次正确改动是否更早。
本次没有完成这项对照，不能声称已验证本体建模的收益。
